# 排错实录（Troubleshooting Notes）

> 记录 weather-travel-agent 开发与联调过程中踩过的真实问题，按「现象 → 根因 → 解法 → 预防」复盘。
> 这些问题与业务逻辑无关，全部属于**环境 / 编码 / 协议 / 进程管理**层面的坑——也是"工具调用稳定性"的实战注脚。

## 1. PowerShell 5.1 调 HTTP 接口的两个编码坑

### 现象
- `Invoke-RestMethod` 收到的中文变成 `åŒ—äº¬` 之类的乱码，`($r.cities -contains "北京")` 返回 `False`；
- `curl.exe -d '{内联中文}'` 请求被服务器以 **422 Unprocessable Content** 拒收。

### 根因
- **响应侧**：`Invoke-RestMethod` 把服务器返回的 UTF-8 JSON 按系统默认代码页（CP1252/GBK）解析成字符串，中文字符在进入 PowerShell 对象的那一刻就已经损坏——不是"显示乱码"，是**数据本身脏了**，事后 `ConvertTo-Json | Set-Content -Encoding utf8` 写文件也救不回来。
- **请求侧**：PowerShell 5.1 向原生 exe（curl.exe）传参时按系统 ANSI 代码页（GBK）编码，curl 把 GBK 字节原样发给服务器，FastAPI 按 UTF-8 解析 JSON 直接失败 → 422。响应体是 `{"detail":[...]}`，读出来 `intent/cities` 全是 `None`。

### 解法
- 请求体走**文件**：`[System.IO.File]::WriteAllText("$PWD\p.json", $json, (New-Object System.Text.UTF8Encoding($false)))` 写 UTF-8（无 BOM），再 `curl.exe -d "@p.json"`；
- 结果用 **Python 读原始文件并打印**：`json.load(open('r.json', encoding='utf-8'))`（Python 输出中文在控制台是正常的），彻底绕开 PowerShell 的字符串解码。

### 预防（排错铁律）
**先看服务端日志的 HTTP 状态码，再决定查哪一层**：422=请求体坏、500=服务内部错、200 但字段空=Agent/LLM 问题。不要一上来就猜编码。

## 2. 设了 DEEPSEEK_API_KEY 但真实 LLM 被代理"掐死"——表现为"功能坏了"

### 现象
`/chat` 返回 200，但 `intent: None`、`cities: None`、`answer: ""`，看起来多智能体功能完全不工作。

### 根因
启动服务的终端里一旦有 `DEEPSEEK_API_KEY`，`config.py` 就置 `USE_REAL_LLM=True` 走真实 DeepSeek；若本机代理（FlClash）开着，API 调用被劫持返回空串 → 意图解析失败默认 `{"action":"chat"}` → 走闲聊兜底分支，**城市抽取根本没有执行**。

### 解法
- 只测功能：`$env:DEEPSEEK_API_KEY = $null` 后**重启 uvicorn**（`config.py` 在导入时缓存，改环境变量不重启不生效），自动回退到离线 mock 模式；
- 要用真实 LLM：先关代理，或启动前清空 `HTTP_PROXY/HTTPS_PROXY` 并设 `no_proxy='*'`。

### 预防
优雅降级（mock 兜底）必须显式可辨：返回体中带上模式信息，避免"mock 正常 / 真实 LLM 静默失败"难以区分。

## 3. 改了环境变量却没杀旧进程——测的还是旧实例

### 现象
按指导清掉 Key 并"重启"服务后，测试结果毫无变化，仿佛操作没生效。

### 根因
新起的 uvicorn 日志显示 `Application startup complete.` 后**立刻** `Shutting down` 秒退；**旧实例仍占着端口**，后续请求全部打到旧进程——所以怎么测都是旧行为。

### 解法与预防
- 换新端口（如 8001）起新实例，绕开端口占用，立刻可验证；
- 去掉 `--reload`：reload 会监听项目目录，测试时往目录里写结果文件（如 `r1.json`）会触发重启干扰；
- 纪律：**一个窗口专跑服务，一个窗口专跑测试**；改环境变量必须确认旧进程真的死了（`netstat -ano | findstr :8000` → `taskkill /F /PID <pid>`）。

## 4. Windows 控制台"快速编辑模式"冻结整个服务

### 现象
请求已送达服务器（curl 显示 `Upload 76` 完成）但 `Received 0`，等了 7 分钟无响应；**连最简单的 `/health` 都挂起**——但连接能建立（是挂起，不是"连接被拒"）。

### 根因
Windows 控制台的**快速编辑模式（QuickEdit）**：只要用鼠标在服务窗口里点击/拖选文字，控制台就进入"选择"状态，**任何程序向该窗口的输出都会被阻塞**。uvicorn 每个请求都要写访问日志 → 日志写不出去 → **整个事件循环冻住** → 所有请求（包括 /health）全部无响应。

### 解法
- 解除：点击服务窗口，按 `Enter`（或 `Esc`）取消选择——服务瞬间复活，积压请求一并完成；
- 根治：窗口标题栏右键 → 属性 → **取消勾选「快速编辑模式」**。

### 预防
跑长服务的控制台窗口，不要随手在里面选字；判断"整体冻结 vs 单请求卡死"的试金石就是 **`/health` 是否还能秒回**。

## 5. MCP 传输层无超时导致请求永久挂起（已修复）

### 现象
一次 /chat 请求上传完成后，服务器 7 分钟不返回任何字节；而天气 HTTP 层设计上最坏 ~51 秒必返回。

### 根因
`utils/weather_client.py` 本身有完善的稳定性设计（8s 超时 × 3 次重试 + 指数退避 + 兜底占位）；但 `mcp/mcp_client.py` 的 `_recv()` 直接对子进程 `stdout.readline()` **无限阻塞**——天气子进程一旦失联（网络抖动/子进程异常），整个 FastAPI 请求**永久挂起**。实测远超 51 秒上界，证明卡点在 MCP 传输层而非 HTTP 层。

### 修复（mcp/mcp_client.py）
- 后台守护线程持续把子进程 stdout 泵进队列，主流程改用**带超时的 `queue.get`**（20s）等待响应，整体受 deadline 约束，**绝不无限阻塞**；
- 子进程管道断裂（写入抛异常）按超时处理；
- 超时/失联 → `get_weather` 返回带 `fallback: True` 的「MCP调用失败」占位，请求正常返回，且编排层不会把失败数据写入长期记忆。

### 面试可讲
> "发现并修复了工具调用链路中**传输层缺超时导致的级联挂起**：HTTP 层有超时重试兜底，但 stdio JSON-RPC 层的 readline 无限阻塞，任何一次子进程失联都会把整个请求挂死。通过『后台泵线程 + 队列 + 带超时等待』重构了接收逻辑，与已有的重试/限流/兜底形成完整的稳定性闭环。"

## 附：通用排错铁律

1. **先看服务端日志状态码**（422/500/200），再决定查哪一层，不要先猜；
2. **不信客户端显示**——用 Python 读原始响应文件，绕开终端编码；
3. **改环境变量必须重启进程**，并确认旧进程真的死了；
4. **服务窗口与测试窗口分离**，跑服务的窗口别用鼠标选字；
5. 每一层外部依赖（HTTP、子进程、RPC）都要有**超时 + 兜底**，缺一层就可能把局部故障放大成全局挂起。
